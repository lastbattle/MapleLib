# LRU cache performance report

## Scope and compatibility contract

This report measures `MapleLib.Img.LRUCache<TKey, TValue>` as used by
`ImgFileSystemManager`. The required behavior is exact least-recently-used promotion
and eviction, item- and byte-capacity enforcement, thread safety, factory-once
`GetOrAdd` behavior, stable statistics, snapshot ordering, and existing disposal
semantics.

Primary metrics are single-thread cached-hit latency, contended cached-hit throughput,
and allocation. Single-thread and contended measurements are kept separate because
lock changes can affect them differently. Changes below 3% or within observed variance
are treated as a plateau.

## Iteration record

### Iteration 0 - baseline harness

- Change: added a BenchmarkDotNet harness only; production code is unchanged.
- Workload: 512 cached IMG-shaped string keys. The single-thread benchmark performs
  1,024 hits per invocation. The contended benchmark performs 1,024 hits per worker
  with 1, 4, or 16 workers.
- Correctness: `dotnet test MapleLib/MapleLib.Tests/MapleLib.Tests.csproj -c Release
  --no-restore --filter FullyQualifiedName~LRUCacheTests` passed 21/21.
- Benchmark command: `dotnet run -c Release --no-build --project
  MapleLib/benchmarks/MapleCrypto.Benchmarks/MapleCrypto.Benchmarks.csproj --
  --filter '*LruCacheBenchmarks*' --artifacts BenchmarkDotNet.Artifacts/lru-baseline`.

| Workload | Mean | Allocation |
| --- | ---: | ---: |
| Single-thread hit | 50.92-52.29 ns/hit | 0 B |
| 1 worker x 1,024 hits | 59.42 us | 1,864 B/invocation |
| 4 workers x 1,024 hits | 405.82 us | 2,705 B/invocation |
| 16 workers x 1,024 hits | 2.002 ms | 5,847 B/invocation |

- Decision: baseline accepted. The repeated single-thread parameter rows agree within
  2.7%; 4- and 16-worker runs show the expected serialization cost and more variance.

### Iteration 1 - remove unused access timestamps

- Proposed change: remove `CacheItem.LastAccess` and its `DateTime.UtcNow` writes. LRU
  order is already represented by the linked list, and no API reads the timestamp.
- Correctness: focused cache tests passed 21/21 after the change.
- Benchmark command: same matrix as iteration 0, with artifacts written to
  `BenchmarkDotNet.Artifacts/lru-no-timestamp`.

| Workload | Baseline | No timestamp | Improvement | Allocation |
| --- | ---: | ---: | ---: | ---: |
| Single-thread hit | 50.92-52.29 ns | 32.02-32.21 ns | 37.1-38.6% | unchanged, 0 B |
| 1 worker x 1,024 hits | 59.42 us | 41.46 us | 30.2% | unchanged, 1,864 B |
| 4 workers x 1,024 hits | 405.82 us | 246.57 us | 39.2% | 2,705 B / 2,693 B |
| 16 workers x 1,024 hits | 2.002 ms | 1.447 ms | 27.7% | 5,847 B / 5,858 B |

- Decision: keep. Removing an unobservable wall-clock query materially improves every
  hit workload without changing the linked-list LRU state or measurable allocation.

### Iteration 2 - single monitor lock candidate

- Proposed change: replace the upgradeable-reader/write-lock pair with one reentrant
  monitor. Every cache hit mutates LRU order, so `TryGet` cannot allow concurrent
  readers; a single monitor avoids the nested lock protocol while preserving serialized
  mutation and factory-once behavior.
- Correctness: focused cache tests passed 21/21 after the change.
- Benchmark command: same matrix as iteration 0, with artifacts written to
  `BenchmarkDotNet.Artifacts/lru-monitor`.

| Workload | RW lock, no timestamp | Monitor | Improvement | Allocation |
| --- | ---: | ---: | ---: | ---: |
| Single-thread hit | 32.02-32.21 ns | 19.27-19.73 ns | 38.5-40.0% | unchanged, 0 B |
| 1 worker x 1,024 hits | 41.46 us | 23.70 us | 42.8% | unchanged, 1,864 B |
| 4 workers x 1,024 hits | 246.57 us | 154.00 us | 37.5% | 2,693 B / 2,681 B |
| 16 workers x 1,024 hits | 1.447 ms | 714.89 us | 50.6% | 5,858 B / 5,829 B |

- Read-only check: the monitor completed 1/4/16-worker `ContainsKey` plus `Count`
  batches in 21.57 us / 275.09 us / 1.696 ms. A same-run reader-lock surrogate took
  27.04 us / 126.10 us / 858.75 us. Although the monitor improved one-worker reads,
  it regressed the 4- and 16-worker read-only workloads by 2.18x and 1.98x.
- Decision: revert the monitor candidate. `ContainsKey`, `Count`, and snapshot APIs
  can use true concurrent readers, and their material high-contention regression is
  unacceptable. Retain only iteration 1's timestamp removal.

### Iteration 3 - direct write lock for `TryGet`

- Proposed change: enter the write lock directly in `TryGet` instead of entering an
  upgradeable read lock and then nesting a write lock on hits. Every hit promotes a
  linked-list node. `ContainsKey`, `Count`, and snapshots retain shared read locks.
- Timestamp: 2026-09-07T21:19:46Z.
- Correctness: focused cache tests passed 22/22. These cover LRU order and eviction,
  item and size limits, statistics, concurrent access, factory-once behavior, snapshot
  order, idempotent disposal, and post-disposal failure for all public operations.
- Benchmark command: `dotnet run -c Release --no-build --project
  MapleLib/benchmarks/MapleCrypto.Benchmarks/MapleCrypto.Benchmarks.csproj --
  --filter '*LruCacheBenchmarks.HotHitSingleThread*'
  '*LruCacheBenchmarks.HotMissSingleThread*' '*LruCacheBenchmarks.ContendedHits*'
  --artifacts BenchmarkDotNet.Artifacts/lru-direct-write`.

| Workload | Upgradeable/write, no timestamp | Direct write | Improvement | Final SD |
| --- | ---: | ---: | ---: | ---: |
| Single-thread hit | 32.02-32.21 ns | 22.18-23.06 ns | 28.0-31.1% | 0.05-0.72 ns |
| 1 worker x 1,024 hits | 41.46 us | 32.75 us | 21.0% | 0.10 us |
| 4 workers x 1,024 hits | 246.57 us | 175.32 us | 28.9% | 2.23 us |
| 16 workers x 1,024 hits | 1.447 ms | 1.426 ms | 1.5%, within prior variance | 0.016 ms |

- A direct-write miss measured 15.75-15.83 ns with 0 B allocation. There is no
  pre-change miss baseline, so no miss speed claim is made.
- Decision: keep. Direct write removes a redundant lock transition on the dominant hit
  path while preserving reader concurrency for the read-only APIs. Allocation is
  unchanged.

## Plateau confirmations

The direct-write single-hit workload was rerun in three separate BenchmarkDotNet
process sets. The stable WorkerCount=1 rows were 22.44 ns (SD 0.096 ns), 21.92 ns
(SD 0.163 ns), and 22.72 ns (SD 0.105 ns), all at 0 B allocation. Results below are
stored beside this report in `results/lru-direct-write*.csv`; baseline and rejected
candidate CSVs are stored there as well.

The optimization is retained at this plateau. The subsequent real
`ImgFileSystemManager.LoadImage` cached-hit benchmark against
`<GMS-v95-corpus>` is recorded in
`2026-09-07-img-manager-cache-key.md`. Its baseline already includes these retained LRU
changes, so the manager result isolates key construction and must not be combined with
the LRU percentage as though both shared the same baseline.
